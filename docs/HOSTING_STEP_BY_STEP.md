# Hosting, step by step

Generated by `scripts/build_hosting_docs.py`; do not edit.

One public repository on GitHub runs AirPulse: its workflow fetches, validates, forecasts when due, builds the site and publishes it on GitHub Pages. After the steps below, no computer of yours takes part. Cost, limits and terms of the provider: `docs/FREE_HOSTING_AUDIT.md`.

## CLAUDE DOES

Done, in the repositories; nothing here needs you.

| What | Where |
|---|---|
| Code: a source that is switched off is not required; the application works under the path of the repository and answers a reload of any route | engine `src/`, `scripts/production_run.py`; application `src/`, `scripts/spa-fallback.mjs` |
| Workflow: one production workflow (three schedules and a manual start) and one for checks on a change | `.github/workflows/production.yml`, `ci.yml` |
| Configuration: the allow-list of the hosted repository and its public profile (sources that may not be published are switched off) | `deploy/public/manifest.yaml` of the research repository; `config/` here |
| Tests: the workflow's order and its stops, the credentials, the allow-list, the checks before an upload, a fixture that must move the site | `tests/test_deployment.py`, `scripts/source_to_site_check.py`, the application's tests |
| Deployment files: the hosted repository itself, assembled and committed, ready to push | the folder named in step 2 |
| Checks before every upload: secrets, development addresses, fields of removed features, deep links, sizes | `scripts/deployment_checks.py` |
| Rehearsal of the whole path on fresh clones, and the documents | `scripts/verify_public_repo.py`; the report in the research repository |

Claude does not create accounts, does not push and does not change settings of a service: those are yours, below.

## USER DOES

Seven steps, once. About fifteen minutes, plus the first run.

### 1. Create a GitHub account and the repository

1. Create a GitHub account at github.com (Sign up), on the free plan. It asks for an e-mail address, which it verifies. The provider's pricing page names no payment card for the free plan; **if a card is asked for at any point, stop and do not enter one**: the design does not need it and something is different from what was read.
2. Create the repository: the plus sign at the top right → New repository. Name: `airpulse` (the name becomes part of the address of the site). Visibility: **Public** (GitHub Pages on the free plan needs it). Do **not** add a README, a .gitignore or a licence: the repository must start empty.

### 2. Push the code

On your computer, once. The folder to push is the hosted repository, `airpulse-public`, beside the two research folders (open a terminal in the folder that holds all three). It is **not** the research repository `AirPlus`, which holds material that may not be made public.

```bash
cd airpulse-public
```

```bash
git remote add origin https://github.com/<account>/airpulse.git
```

```bash
git push -u origin main
```

A browser window opens for you to sign in to GitHub. Replace `<account>` by your account name.

Optional, before the push: the one commit in that folder carries the name and the e-mail address of your git configuration, and a public repository shows them. To show GitHub's no-reply address instead: GitHub → Settings → Emails → tick "Keep my email addresses private" and copy the address ending in `@users.noreply.github.com` shown there; then, in the folder, `git config user.email "<that address>"` and `git commit --amend --reset-author --no-edit`, and push.

### 3. Enable Actions

Repository → Settings → Actions → General. "Allow all actions and reusable workflows" is the default for a new repository; leave it. Nothing else is needed: the workflow states the permissions of each of its jobs itself. (If the first run stops at the step "Commit the operational state" with "permission denied", set Workflow permissions on that page to "Read and write permissions" and run again.)

The first push starts the workflow `ci` by itself (Actions tab). It checks the code and publishes nothing; it takes about 20 minutes and should end green.

### 4. Enable Pages

Repository → Settings → Pages → Build and deployment → Source: **GitHub Actions**. Nothing else on that page. Do this before step 6: without it the run stops at the step "Address the site is served under", after it has committed the day's data and before it builds.

### 5. Add secrets

None. No source needs a key, and the workflow uses no secret and no variable. Leave Settings → Secrets and variables empty.

### 6. Trigger the first workflow

Repository → Actions → production (left column) → Run workflow → Run workflow. Leave the field empty. The run takes about 20 to 30 minutes and has three jobs: "Refresh, validate, test, build", "Deploy to GitHub Pages", "Every production source healthy".

### 7. Verify the address of the site

Repository → Settings → Pages shows the address of the site, `https://<account>.github.io/airpulse/`. Open it and check four things:

1. the home page loads with its images;
2. Data (top right) lists the sources with the date of the last run, which should be the run you just started;
3. Monthly outlook shows the current outlook and its record;
4. on any inner page, reload the browser: the same page comes back.

From here the schedules run by themselves: daily at 07:11 UTC, Mondays at 08:23 UTC, and on the 23rd at 09:31 UTC. Until GitHub's scheduler has started a run, the site says Snapshot; after the first scheduled run it says so from the run record, not from a setting.

## After that: nothing on your computer

What you may want to look at, from any browser or phone:

- **The site.** Its Data page shows the state of every source and of the last run.
- **An e-mail from GitHub about a failed run.** Open the run. If only the job "Every production source healthy" failed, a source was late or unreachable: the site was still deployed and names it; the next run tries again, and nothing is needed from you unless it repeats for days. If the job "Refresh, validate, test, build" failed, nothing was published and the site kept its last state; its summary shows the last hundred lines.
- **An e-mail saying a scheduled workflow was disabled.** GitHub switches schedules off in a public repository after 60 days without repository activity. Actions → production → Enable workflow.

## Emergency and manual recovery only

None of this is part of normal operation.

| Situation | What to do | Where |
|---|---|---|
| A run failed and you want to try again now | Actions → the failed run → Re-run all jobs | browser |
| You want a source asked now although it is not due | Actions → production → Run workflow, and type the group in the field: `fuel`, `bls`, `weekly` or `aviation` | browser |
| The site must go back to an earlier state | Actions → an earlier successful production run → Re-run all jobs (GitHub Pages also keeps the last successful deployment when a run fails) | browser |
| A day of data must be undone | on the repository page, open the commit "operations: production run" of that day → Revert; the next run verifies the chains again | browser |
| The code must change | change it in the research repositories, run their checks, then `python scripts/build_public_repo.py <clone of the hosted repository> --update` and push | your computer |
| The repository nears 1 GB (years away; every run prints its size) | start it afresh from its current state: see the storage section of `docs/FREE_HOSTING_AUDIT.md` | your computer |
